# 0017. cheatsheet-review: a multi-model pull request reviewer started by the operator's label

- Status: accepted
- Date: 2026-10-29
- Deciders: Jakub Maćkowski

## Context

The OWASP Cheat Sheet Series receives many pull requests of uneven quality, some generated by AI with
sources that do not exist or do not support the claim. Upstream already describes how a review
should be done: `MODELS.md` (several independent reviewers from different model families, a
separate decision step, no silent model substitution), `.claude/commands/review-cheatsheet-pr.md`
(five dimensions: security, practicality, links and sources, duplication, language; a single
MERGE / REQUEST_CHANGES / CLOSE verdict) and `.github/skills/code-review/SKILL.md` (match the depth
to the change: a link swap does not need five dimensions).

The operator wants that review on demand: adding the `custodes_cheatsheet_review` label to a pull
request starts it, but only when the operator's own account (`mackowski`) adds it. The result is
posted as a GitHub review with inline `suggestion` blocks, clearly marked as an LLM review the author
may disagree with. A low-quality pull request also produces an e-mail to the operator recommending
to close it and unassign the author from the issue; the agent itself does neither.

No broker action could post inline comments (`pr.review` sends only an event and a body), and no read
returned a single pull request or a file at the pull request's head commit.

## Decision

We will add a `cheatsheet-review` agent and the broker capabilities it needs:

- **Trigger.** A `pull_request.labeled` webhook whose label and sender match the instance's
  configuration wakes the agent. The webhook is only a hint: the agent re-reads the pull request and
  its timeline through the broker and runs only if the trigger label is still present and the latest
  `labeled` event for it was made by the configured actor. Each label event is reviewed at most
  once; re-adding the label asks for a new review.
- **Mode `hotl`, sandbox first.** Every run is started by the operator, so the label is the human
  decision to publish; there is no further approval. This departs from "new agents start `hitl`"
  (ADR 0004). The policy entry ships as `hitl` with the broker change and switches to `hotl` only in
  the pull request that adds the agent, its label and actor check, and its evals, so the grant is
  never live without the code that justifies it. The policy lists only `mackowski/custodes-sandbox` until the agent's evals reach 90%
  with no injection leak, three sandbox end-to-end runs pass (links only, code, low quality), and the
  operator has reviewed the first five reviews. Adding `OWASP/CheatSheetSeries` is a separate,
  reviewed policy change. There is no daily review cap; the broker's 20 per hour per repository is
  a fuse against a bug, not a budget. Label removals count against it too, so it allows about ten
  reviews an hour.
- **Broker action `pr.review.inline`.** One review pinned to a full commit SHA, with at most 20
  RIGHT-side comments (optionally multi-line). Its event is `COMMENT` or `REQUEST_CHANGES`; `APPROVE`
  is not in the schema. The agent asks for changes only when a security or links reviewer found a
  blocker; everything else, including a CLOSE verdict, is a comment. The agent cannot dismiss its own
  earlier review; the operator does that.
- **Reads `pull` and `pull_file_at_ref`.** The second returns a file under `cheatsheets/` or
  `cheatsheets_draft/` (one level, validated name) at any 40-character SHA. This is the first read
  with a caller-supplied path (ADR 0010 allowed only file names); the schema bounds it and the broker
  still builds the URL. The broker does not check that the SHA is the pull request's head.
- **Label scope.** A new optional `labels` allow-list in the agent policy limits `issue.label.add`
  and `issue.label.remove`; for this agent it is only `custodes_cheatsheet_review`, so it cannot
  remove a maintainer's triage labels.
- **Token.** A separate PAT, `PAT_CHEATSHEET_REVIEW`. While the policy lists only the sandbox it is a
  fine-grained PAT for `mackowski/custodes-sandbox` alone (Pull requests and Issues: read and
  write). The pull request that adds OWASP replaces it with a classic `public_repo` PAT, for the same
  reason as `PAT_PR_GATE` (ADR 0011 amendment: no fine-grained PAT for the OWASP organisation). The
  broker allows it only `pr.review.inline` and `issue.label.remove`.
- **Models.** Depth follows the change: deterministic rules first, a small model only for ambiguous
  prose. Links-only and minor prose changes get the links and language reviewers; content and code
  changes get all five dimensions plus a second security reviewer. Every reviewer sees the same
  frozen snapshot and none sees another's findings; a judge from another model merges them.
  - Lineup: Claude Haiku 5.5 (scope), DeepSeek V4.1 Flash on Workers AI (links), GPT-6 Luna
    (language), Muse Spark 1.3 (practicality, duplication), Claude Opus 5.5 (security), DeepSeek V4
    Pro on Workers AI (second security voice), GPT-6.1 Sol (judge).
  - Fallbacks are allowed but never silent: the review header names the model that failed and the
    one used instead. After fallbacks, the two security voices must come from different vendors and
    the judge must be a third model; otherwise nothing is published and the partial review is
    e-mailed to the operator.
- **Transport.** Anthropic through the existing `AnthropicGateway`, Workers AI through the binding
  with a gateway id, and OpenAI and Meta models through AI Gateway's OpenRouter provider with the
  key stored in the gateway (BYOK). Every call stays on one AI Gateway (ADR 0015). A Diagnose step
  calls each model for real before the agent depends on it; if the gateway cannot reach OpenRouter's
  chat endpoint, the operator decides the exception.
- **External links.** The agent fetches the external links a pull request adds (https only, at most
  15, 10 s, 2 MB, 5 redirects). Only the links reviewer sees page text, wrapped with `untrusted()`,
  and it answers with a fixed verdict enum. 401, 403, 429 and 5xx mean "verify manually", never
  "broken".

## Alternatives considered

- **`hitl` with an e-mailed approval before posting.** The label is already a per-run human decision,
  and no agent uses the approval flow yet; the cost would be a second round trip for every review.
- **Always `COMMENT`.** The operator wants a blocking review when advice is dangerous or a source is
  fabricated.
- **Reusing `PAT_PR_GATE`.** The audit log could no longer tell the two agents apart (ADR 0003).
- **Extending `pr.review` with comments.** It allows `APPROVE`, and widening it would widen every
  agent that is ever granted it; a separate action keeps the grant explicit.
- **All models through OpenRouter, or Cloudflare Unified Billing.** The first moves Anthropic off the
  existing BYOK key and the second needs wholesale billing, which ADR 0005 turns off.
- **Silent fallback, or no fallback.** Silent substitution is what `MODELS.md` forbids; no fallback
  would let one provider outage turn every review into an e-mail.
- **A size or daily cap.** The operator chooses which pull requests to label and accepts their cost.
- **Closing the pull request or unassigning the author automatically.** Both stay with the operator,
  who receives the recommendation by e-mail.

## Consequences

- The operator gets an upstream-style review on demand, at a depth that matches the change, for
  roughly $0.5 to $1.5 per full review and a few cents for a link fix.
- Reviews appear under the operator's name. A `REQUEST_CHANGES` review blocks merging until the
  operator dismisses it or reviews again, and other maintainers will see it; the operator tells the
  OWASP maintainers before the agent is enabled there, and every review links to the agent's page.
  Inline comments carry no trailer (only the review body does), so the broker marks each one as an
  LLM suggestion, and no agent may count review comments by the operator's account as the
  operator's own words.
- GitHub refuses `REQUEST_CHANGES` on a pull request by the token's owner, so on the operator's own
  pull requests (sandbox tests) the agent posts `COMMENT`.
- Four model providers mean four ways to fail; fallbacks and the vendor invariant keep reviews
  multi-model, at the cost of an occasional e-mail instead of a review.
- The deploy now syncs agent PATs into Secrets Store before deploying the broker, so a new binding
  resolves on its first deploy. The `github-pat-cheatsheet-review` entry is created by that sync, not
  by Terraform; adding the agent to Terraform's `agents` later needs a `terraform import` first. The
  GitHub secret must exist before this merges, or the broker deploy fails.
- Policy `tokenBinding` names must now start with `PAT_`, and the sync script refuses other names,
  so a policy typo can never copy another CI secret into Secrets Store.

## Security considerations

- **Authority.** A second write-capable agent. On the sandbox its fine-grained PAT reaches only that
  repository; once OWASP is added, its classic PAT could, on GitHub's side, push to any public
  repository the operator can write to, including OWASP. The broker limits it to two actions, one
  label, signs and audits each one, and rate-limits it; the PAT is rotated every
  90 days (`docs/runbooks/rotate-pat.md`). This revisits the threat model's accepted risk for a second
  write agent sharing the Worker; the risk is accepted again for the same reason as pr-gate's.
- **`hotl` without a broker-side check of the trigger.** The broker never sees the label, so "the
  operator started this run" is enforced by agent code; a compromised agent in the Worker could post
  as cheatsheet-review without it. The sandbox-only policy (pinned by a test) and the rate limit
  bound that until the OWASP widening, which sets `requiresApproval: ["pr.review.inline"]` for the
  first five OWASP reviews.
- **Inline comments.** They post under the operator's account and carry no trailer, so the broker,
  not the agent, prefixes each one with a fixed "Custodes LLM suggestion" marker. A steered model
  cannot post an inline comment that reads as the operator's own.
- **Label grants.** The policy schema refuses a label action without a `labels` allow-list.
- **Trigger spoofing.** The sender in the webhook is HMAC-verified but treated as a hint; the GitHub
  timeline's `labeled.actor` decides. Anyone else adding the label causes no action.
- **Prompt injection.** The pull request body, diff, file contents, file names and fetched pages are
  all author-controlled and reach prompts only through `untrusted()`. Model output is parsed with
  `parseStructured()` and then checked by code: suggestions only on changed lines of changed files,
  `@` mentions neutralised, and URLs kept only if the links reviewer fetched them. The review body is
  rendered by code, never written by a model.
- **Egress.** Fetching author-supplied URLs reveals Cloudflare egress addresses to those sites and
  costs time; the limits above bound it. Workers cannot reach private networks, so this is not an
  SSRF path into Custodes.
- **Kill switch.** `guard()` runs before every model call, link fetch, broker action and e-mail.

## Amendment 2026-10-30: lineup after the benchmark

A one-off benchmark on 30 OWASP pull requests (`workers/agents/scripts/benchmark/REPORT.md`, run
by hand, not in CI) changed four roles:

- **Second security voice:** DeepSeek V4.1 Flash at high reasoning effort replaces V4 Pro. It found
  7 maintainer-raised problems against 4, and had no Workers AI timeouts; V4 Pro timed out (HTTP 408) on 4 to 8 of 27 pull requests. The fallback is the same weights on OpenRouter, restricted to
  hosts serving fp8 or better.
- **Practicality:** Claude Sonnet 5.5 replaces Muse Spark 1.3 (13 problems found against 2).
- **Judge:** GPT-6 Astra replaces GPT-6.1 Sol by the operator's preference: on the same 17 pull
  requests Astra agreed with the maintainers' outcome 14 times, Sol 13, which is within noise.
- **Fallbacks:** Opus falls back to Sol (Astra is now the judge); Muse Spark falls back to Sol
  instead of Llama 4 Maverick, which had no evidence behind it.

Rejected: Muse Wonder as a third security voice (no problem found that Opus or DeepSeek missed, 4
false blockers). Not measured: the duplication checker (needs repository-wide retrieval) and the
link auditor (the linked pages have changed since).

## Amendment 2026-10-30: the operator approves each review on OWASP

On OWASP a review is posted only after the operator has read it and clicked Approve. Policy gets
`requiresApprovalOn` per repository; cheatsheet-review lists `pr.review.inline` for OWASP and, until
the flow has passed its end-to-end run there, for the sandbox.

1. The broker answers the review with `approval_required`. The agent asks for an approval
   (`POST /v1/approvals`) and gets a token, e-mails the operator a link with only code-computed
   facts in it, removes the trigger label and records `awaiting_approval`.
2. The link opens `custodes.work/admin/approvals/link/<token>` behind Access. Only a person on
   `APPROVER_EMAILS` may open it. GET shows the stored review, HTML-escaped, without script, links
   or framing; only the POST buttons decide, so a mail scanner opening the link decides nothing.
3. The token is an HMAC over the approval id, agent, action hash and expiry (24 h). The key is
   generated inside the broker's `Keyring` and never leaves it, so no Worker and no CI secret holds
   it; `APPROVAL_TOKEN_SECRET` is gone. A token opens only its own approval's exact action.
4. On approval the broker runs the stored request itself through `act()` (kill switch, rate limit,
   execute, signed audit), once. A second click finds the approval no longer pending. If the author
   pushed in the meantime, the review still goes to the commit it was written for.

The broker now has two entrypoints. Agents bind the default one: act, read, and asking for an
approval. Only the gateway binds `BrokerAdmin`: deciding approvals, the audit log and keys. Before,
any caller of the broker's service binding, the agents Worker included, could decide an approval or
rotate a key.

An approval is single-shot: after the decision the broker consumes it whether or not the post
went through (halted agent, rate limit, GitHub error), and the agents' entrypoint refuses any
request that carries an `approvalId`. By id (CLI) an approval can only be rejected; approving
needs the link page, which shows the action. A halted agent cannot ask for approvals, and an agent
may have at most 20 pending.

Replies to `approve+…@` and `reject+…@` addresses are refused. Mail addresses are case-folded, which
breaks a base64url token, and a reply cannot prove who clicked as Access does.

Rejected: a bare link without a token (Access alone does not bind the click to the action shown);
waking the agent to post a draft kept in its storage (more state, same outcome); the token secret
as a CI secret (the Keyring already keeps keys that never leave the broker).

## Amendment 2026-10-30: enabled on OWASP

`OWASP/CheatSheetSeries` is added to the agent's repositories, reads and instances, with the same
trigger (the operator's `custodes_cheatsheet_review` label). Every OWASP review waits for the
operator's approval on the e-mailed link; the sandbox entry is removed from `requiresApprovalOn`, so
the sandbox posts directly for quick end-to-end runs. Preconditions met: all eval suites at 100%,
sandbox end-to-end runs, and the approval link run on sandbox#64. Operator steps before merging:
`PAT_CHEATSHEET_REVIEW` becomes a classic `public_repo` PAT, the label exists on OWASP, and the
OWASP maintainers are told.
