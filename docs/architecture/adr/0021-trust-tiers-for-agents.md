# 0021. Trust tiers for agents

- Status: accepted
- Date: 2026-11-23
- Deciders: Jakub Maćkowski

## Context

Today's agents are workflows with one model step. The next ones (#131) are model-driven loops
with more autonomy: backlog-review (#132) acts HOTL on most of the OWASP backlog and pushes
code-computed fixes; self-improvement (#133b) and issue-implementer (#134) author content. Without a
shared scale, every new agent reopens the same questions: does it need a bot identity, guardrails,
garak, a supervisor, a sandbox?

`AgentMode` (`hitl | hotl | readonly`, ADR 0004, ADR 0009) answers a different question: who
approves. It cannot say that triage-apply (comments, HITL) and a future agent writing cheat sheets
(HITL too) need different controls. Policy v2 (#139) adds a per-action `risk`, which answers a
third question: how bad a single action can be.

All PATs are classic `public_repo` tokens on the operator's account (ADR 0003, ADR 0011), so any of
them could push to OWASP. What an agent can do is bounded by broker policy, not by the token.

Decisions were taken in a `/grill-plan` round on #138.

## Decision

We will describe every agent along three separate axes:

- **Tier**: what the agent can do (capability). The agent's tier is the highest tier of the broker
  actions its policy grants.
- **Mode**: who approves, **per action class**. An agent has a default mode; action classes can
  need approval (`requiresApproval`, `requiresApprovalOn`), and an agent can escalate a single
  action to HITL at run time but never de-escalate one.
- **Risk**: how bad one action can be, per action, in the action registry of #139. A riskier action
  does not raise the tier.

**Tiers.** The line between T1 and T2 is who wrote the bytes that land in the repository, not the
kind of write.

| Tier | Capability                                                                                                                                                                                                                                 | Today                                           |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------- |
| T0   | Read through the broker and report to the operator.                                                                                                                                                                                        | triage, implementation-check, proposal-review   |
| T1   | Thread and state actions (comment, label, assign, close, approve, merge), and repository writes whose content is computed by code and whose diff the broker verifies (for example `branch.update`, `index.restore`, `lint.autofix`, #132). | pr-gate, triage-apply; backlog-review (planned) |
| T2   | Model-authored content that can land in repository files: inline suggestions, commits, pull requests.                                                                                                                                      | cheatsheet-review                               |
| T3   | Executes code that is not ours (from a pull request, or generated by a model).                                                                                                                                                             | none                                            |

`readonly` mode always means T0.

**Controls by tier.** Each tier adds to the one below.

| Tier | Required controls                                                                                                                                                                                                                                                                                                                         |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T0   | Reads only through `/v1/read`; `untrusted()` and `parseStructured()`; `guard()` before every model call and report; evals with injection cases.                                                                                                                                                                                           |
| T1   | Policy entry, kill switch, rate limits, signed attestation. May act under the operator's account with the broker's visible trailer (hidden only for `hitl` + `bundleOnly`, ADR 0019). A code-computed write has a broker diff validator and a snapshot check, and goes only to a pull request's head branch, never to the default branch. |
| T2   | Before the first T2 write **outside the sandbox repository**: a bot identity (#141), output guardrails (#136), a garak baseline (#137), broker content constraints (paths, size, new link domains; #139), a review gate (cheatsheet-review plus the operator's approval), and the supervisor (#135) if the agent runs a loop.             |
| T3   | A sandbox with no credentials and network only to the broker and AI Gateway (#142).                                                                                                                                                                                                                                                       |

**Approve and merge.** They are T1 by capability, and the riskiest T1 actions (#139). No agent has
them today: `pr.review` was retired because it could approve (`security-controls.md`), and the
threat model accepts the operator's admin-account PAT only because no agent can approve or merge. A
`pr.approve` or `pr.merge` action therefore needs its own ADR that amends that accepted risk; merge
stays HITL (#132).

**What unlocks HOTL** (mode axis, any tier above T0). An action class moves from HITL to HOTL only
when (1) its hard limits are enforced by the broker in code with tests, not by the prompt, (2) it
has evals including injection cases, and (3) it has reached an agreement threshold in a shadow run.
pr-gate went HOTL before (3) existed (ADR 0011, ADR 0013); the rule applies from now on.

**A loop is not a tier.** Every agent that runs a model loop (#140) needs round and budget caps,
checks on tool calls, and `untrusted()` on tool results, at every tier including T0.

**Triggering automation.** Adding a label from `AUTOMATION_TRIGGER_LABELS` does not change an
agent's tier, but no agent may add one today (ADR 0019, policy test): with the operator's PAT the
label passes as the operator's, and cheatsheet-review's hotl mode rests on the label being the
operator's decision (ADR 0017). `jules` stays banned for every agent. The handoff backlog-review
needs (#132, update 2) comes with its own ADR that amends ADR 0017 and ADR 0019 with: cheatsheet-review
telling an agent-added label from the operator's (for example by the broker attestation of that
`issue.label.add`), approval on every repository for agent-started runs, at most one run per head
SHA, and a daily cap.

**cheatsheet-review exception.** It is T2 and posts under the operator's account without
guardrails, garak or content constraints. This is accepted while every OWASP review needs the
operator's approval (`requiresApprovalOn`), which makes each one the operator's own review. If that
approval is removed, the exception lapses and the T2 controls apply.

**Enforcement.** This ADR defines the scale. Enforcement in code belongs to #139 (the action
registry carries `tier` next to `risk`, and CI checks that an agent's declared tier equals the
highest tier of its actions) and #140 (`tier` in `agent.md` is checked against policy). The broker
already enforces actions, so it does not check tiers per request.

## Alternatives considered

- Tiers replace `AgentMode`: cannot express "T1 with HITL" (triage-apply) or per-action-class modes
  (#132).
- Tier by kind of write (every commit or suggestion is T2): makes backlog-review T2 for fixes that
  carry no model-authored bytes.
- Tier raised by risk: every risky T1 action (merge, approve) would pull its agent into T2 controls
  that address model-authored content, not risk.
- Every trigger inherits the target's tier: makes backlog-review T2 for adding the cheatsheet-review
  label; the label is controlled by its own rules instead (above).
- Allowing the cheatsheet-review label for our agents in this ADR: cheatsheet-review cannot tell an
  agent's label from the operator's, so it would pre-authorise what ADR 0017 and ADR 0019 forbid
  (security review of #162).
- The broker checks the tier on each request: duplicates action enforcement it already does.
- A `tier` field and CI checks now: #139 and #140 replace the policy schema and the agent
  definition, so they would be reworked within weeks.

## Consequences

- New agents get their controls from their tier instead of a per-agent debate. backlog-review can
  run HOTL as T1 under the operator's account without waiting for #141; its label handoff and any
  approve or merge still need their own ADRs (above).
- #134 and #133b can be built on the sandbox; their first OWASP write waits for every T2 control.
- #142 (sandbox) is not needed until an agent reaches T3.
- Agent pages and `docs/agents/README.md` show a tier next to the mode.
- Until #139 and #140 land, the tier is documented, not checked in CI: a policy change that adds a
  T2 action to a T1 agent is caught only in review (invariant 4 still applies).

## Security considerations

- Authority stays with broker policy; the tier is a label derived from it, so it adds no new path
  to authority. Its value is that a tier change is visible: granting a T2 action is a tier change
  and needs this ADR's T2 controls, not only the ADR link invariant 4 asks for.
- The T1/T2 line puts model-authored repository content behind a bot identity, guardrails and a
  review gate, the main threat for #134 (poisoned security guidance).
- Making HOTL depend on broker-enforced limits follows the manual backlog run (#132): a rule in the
  prompt was broken, a rule in code never was.
- Accepted gap: cheatsheet-review lacks guardrails, garak and content constraints (see the
  exception above); it is the first target of #136 and #137.
